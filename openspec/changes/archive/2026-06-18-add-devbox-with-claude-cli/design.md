## Context

The repo currently has no standardised local dev environment. Developers must manually install the correct .NET SDK version, Node.js, and any AI tooling. Devbox (by Jetify) provides a `devbox.json`-driven, Nix-backed hermetic shell that pins exact package versions — similar to `package.json` for system tools. Claude CLI (`@anthropic-ai/claude-code`) is an npm package that requires Node.js, making devbox a natural host.

## Goals / Non-Goals

**Goals:**
- Pin the .NET SDK version used for development so contributors get the same toolchain
- Make Claude CLI available inside `devbox shell` without polluting the host system
- Optionally support VS Code Dev Containers / GitHub Codespaces via `.devcontainer/devcontainer.json`

**Non-Goals:**
- Replacing Docker-based CI/CD (the existing `Dockerfile` stays unchanged)
- Enforcing devbox for all contributors (it remains opt-in)
- Managing runtime secrets or environment variables (still done via `.env` / shell exports)

## Decisions

### D1: Use devbox (Jetify) over alternatives (asdf, nix flakes, mise)

**Decision**: devbox  
**Rationale**: Declarative `devbox.json` with a single `devbox shell` command; friendlier UX than raw Nix; growing adoption in the .NET OSS community; native Dev Container integration via `devbox generate devcontainer`.  
**Alternatives considered**:
- *asdf*: no Nix isolation, plugin-per-tool model is more fragile
- *nix flakes*: more powerful but steep learning curve; overkill for this use case
- *mise*: excellent but no built-in Dev Container generation

### D2: Install Claude CLI via npm inside devbox (not as a Nix package)

**Decision**: Add `nodejs` (LTS) as a devbox package and install `@anthropic-ai/claude-code` globally via npm in a `devbox.json` `init_hook`.  
**Rationale**: Claude CLI is published as an npm package and is not yet in the Nixpkgs registry. Using `init_hook` runs once per `devbox shell` activation and is the idiomatic devbox pattern for npm globals.  
**Alternatives considered**:
- Custom Nix derivation: correct long-term but unnecessary complexity today
- Separate shell script: less discoverable, not tied to the devbox lifecycle

### D3: Include `.devcontainer/devcontainer.json` generated by devbox

**Decision**: Add a `.devcontainer/devcontainer.json` pointing to the devbox image.  
**Rationale**: Zero extra effort (`devbox generate devcontainer` produces it); enables one-click Codespaces for contributors; VS Code Remote-Containers users get the same environment.

## Risks / Trade-offs

- **Nix daemon required on macOS/Linux**: devbox installs its own Nix daemon on first run. This is transparent but requires a one-time `curl | sh` bootstrap. → Mitigation: document in README; devbox install is idempotent.
- **`init_hook` re-runs on every shell activation**: `npm install -g @anthropic-ai/claude-code` will check/upgrade on each `devbox shell`. → Mitigation: acceptable for a CLI tool; can be pinned with `@version` suffix if churn becomes an issue.
- **Devbox lock file drift**: `devbox.lock` pins Nix store hashes; it must be committed and kept up to date. → Mitigation: treat like `package-lock.json` — commit it, update intentionally.
